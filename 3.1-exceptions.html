1 — Warum Exceptions?

Exceptions sind ein Sprachmittel von Java, um Fehler- und Ausnahmesituationen geeignet zu behandeln. Die Ausnahmebehandlung ermöglicht es oft, das Programm auch in solchen Situationen fortzusetzen, und sie informiert andere Programmteile über aufgetretene Fehler.

Bisher gab es in den Set-Methoden im else-Zweig nur ein System.out.println. Das ist keine vollständige Fehlerbehandlung: Es ist nur eine Ausgabe (die vielleicht niemand sieht), und vor allem erfahren andere Programmteile – die Aufrufer der Methode – nichts vom Fehler. Künftig werden stattdessen Exceptions geworfen – und zwar, wie in Lektion 3.0 besprochen, als Guard Clause gleich am Anfang der Methode.

Für das begleitende Beispiel Firma definieren wir eine Klasse FirmaException, die von Exception ableitet. In allen Fehler- und Ausnahmesituationen werden künftig Instanzen dieser Klasse verwendet.

FirmaException.java Java 
public class FirmaException extends Exception {

    public FirmaException(String message) {
        super(message);
    }

    public FirmaException(String message, Exception e) {
        super(message, e);
    }
}

Der zweite Konstruktor nimmt eine auslösende Exception (cause) mit – nützlich, wenn eine technische Exception (z. B. ein Dateifehler) in eine fachliche FirmaException „umgewandelt“ wird (Lektion 3.3).

2 — throw und throws

Das Schlüsselwort lautet throw, gefolgt von new und dem Namen einer Exception-Klasse. Nach throw wird die Methode sofort verlassen – die Exception wird an den Aufrufer durchgereicht.

Person.java – erster Versuch Java 
public void setName(String name) {
    if (name == null || name.isEmpty()) {
        // System.out.println("Fehler: ungueltiger Name: " + name);
        throw new FirmaException("Fehler: ungueltiger Name: " + name);
    }
    this.name = name;
}
Compiler Text 
Person.java:23: error: unreported exception FirmaException; must be caught or declared to be thrown
            throw new FirmaException("Fehler: ungueltiger Name: " + name);
            ^

Der Compiler zeigt nun einen Fehler an (in der IDE: Unhandled exception: FirmaException). Die vorgeschlagene Lösung (Add exception to method signature) fügt im Methodenkopf throws FirmaException hinzu:

Person.java – mit throws Java 
public void setName(String name) throws FirmaException {
    if (name == null || name.isEmpty()) {
        // System.out.println("Fehler: ungueltiger Name: " + name);
        throw new FirmaException("Fehler: ungueltiger Name: " + name);
    }
    this.name = name;
}

Diese Deklaration stellt sicher, dass jeder Aufrufer die potenziell auftretende Exception in irgendeiner Form behandeln muss. Daher zeigt der Compiler den Fehler nun auch im Konstruktor an, der setName verwendet:

Person.java – Konstruktor Java 
public Person(String name, int geburtsjahr) {
    setName(name);              // Fehler: Unhandled exception: FirmaException
    setGeburtsjahr(geburtsjahr);
}
Compiler Text 
Person.java:14: error: unreported exception FirmaException; must be caught or declared to be thrown
        setName(name);
               ^

Da der Fehler im Konstruktor kaum sinnvoll behandelt werden kann, wird auch beim Konstruktor throws FirmaException deklariert:

Person.java Java 
public abstract class Person implements Comparable<Person> {
    private String name;
    private int geburtsjahr;

    public Person() throws FirmaException {
        setName("n/a");
        setGeburtsjahr(1900);
    }

    public Person(String name, int geburtsjahr) throws FirmaException {
        setName(name);
        setGeburtsjahr(geburtsjahr);
    }

    public String getName() {
        return name;
    }

    public void setName(String name) throws FirmaException {
        if (name == null || name.isEmpty()) {
            throw new FirmaException("Fehler: ungueltiger Name: " + name);
        }
        this.name = name;
    }

    public int getGeburtsjahr() {
        return geburtsjahr;
    }

    public void setGeburtsjahr(int geburtsjahr) throws FirmaException {
        if (geburtsjahr < 1900 || geburtsjahr > 2050) {
            throw new FirmaException("Fehler: ungueltiges Geburtsjahr: "
                                     + geburtsjahr);
        }
        this.geburtsjahr = geburtsjahr;
    }

    public abstract int getKostenProMonat();

    // compareTo und toString unveraendert zur vorigen Version
}

Unterklassen

Auch die Konstruktoren von Mitarbeiter, Angestellter, Arbeiter und Freelancer rufen Set-Methoden bzw. super(…) auf, die werfen können – sie brauchen daher ebenfalls throws FirmaException.

3 — try und catch

Wo sollen die geworfenen Exceptions gefangen werden? Eine geeignete Stelle wäre z. B. die Benutzeroberfläche einer Personalverwaltung, die die Datenklassen (Person, Mitarbeiter, …) im Hintergrund als Modell verwendet: Bei einer fehlerhaften Eingabe ruft die Oberfläche die Set-Methode auf, dort wird eine Exception geworfen, die Oberfläche fängt sie und zeigt eine Fehlermeldung an (Teil 4).

Bisher werden die Modellklassen nur in Testklassen verwendet – also muss dort die Fehlerbehandlung stattfinden:

TestFirma.java Java 
public static void testEinstellen() {
    try {
        Arbeiter arb1 = new Arbeiter("Karl", 1989, 15, 40, false);
        Angestellter ang1 = new Angestellter("Susanne", 1991, 20, 30, false);
        Freelancer fl1 = new Freelancer("Sepp", 1981, 3, 300);

        Firma firma = new Firma("Spengergasse OG");

        firma.einstellen(arb1);
        firma.einstellen(ang1);
        firma.einstellen(fl1);

        firma.print();

        // Hier wird eine Exception geworfen
        Arbeiter arb2 = new Arbeiter("Karl", 1789, 15, 40, false);

        firma.print();

    } catch (FirmaException e) {
        System.out.println("EXCEPTION: " + e.getMessage());
    }
}

Die betroffenen Anweisungen stehen in einem try-Block. Im direkt folgenden catch-Block wird angegeben, welche Exceptions behandelt werden; zu einem try darf es auch mehrere catch-Blöcke geben. Die eigentliche Fehlerbehandlung findet im catch-Block statt – hier vorerst eine Ausgabe. Die Fehlermeldung liefert getMessage().

Bis auf die vorletzte Zeile des try-Blocks wird keine Exception geworfen. Dort führt das ungültige Geburtsjahr 1789 zu einer FirmaException. Das folgende firma.print() wird nicht mehr ausgeführt: Nach einer Exception geht es direkt im catch-Block weiter.

💡
In JUnit-Tests

Dass eine Exception geworfen wird, prüft man mit assertThrows(FirmaException.class, () -> new Arbeiter("Karl", 1789, 15, 40, false)); – der Teil nach -> ist ein Lambda-Ausdruck (Lektion 3.5).

4 — Checked vs. unchecked Exceptions

Die bisherigen Exceptions sind checked Exceptions: Der Compiler stellt sicher, dass sie behandelt werden. Deshalb musste bei jedem throw new FirmaException im Methodenkopf throws FirmaException stehen, und deshalb erzwingt der Compiler, dass solche Methoden letztlich in einem try-catch-Block aufgerufen werden.

Das ist besonders sicher, kann aber Nachteile haben: throws-Deklarationen und try-catch-Blöcke an sehr vielen Stellen können Lesbarkeit und Wartbarkeit verschlechtern. Deshalb gibt es auch unchecked Exceptions, deren Behandlung und Deklaration der Compiler nicht erzwingt. Alle Exceptions, die von Error oder RuntimeException ableiten, sind unchecked.

Die Exception-Hierarchie (Ausschnitt) Text 
Throwable
├── Error                         (unchecked – schwere Fehler, z. B. OutOfMemoryError)
└── Exception                     (checked)
    ├── IOException, FirmaException, ...
    └── RuntimeException          (unchecked)
        ├── NullPointerException
        ├── ArrayIndexOutOfBoundsException
        └── NumberFormatException, IllegalArgumentException, ...

Im Zusammenhang mit Frameworks wird oft der Ansatz mit unchecked Exceptions bevorzugt. Für den Einstieg empfehlen wir aber checked Exceptions, da sie die Fehleranfälligkeit etwas reduzieren.

5 — finally

Nach einem try-Block folgen ein oder mehrere catch-Blöcke. Zusätzlich kann ein finally-Block angegeben werden: Er wird in jedem Fall ausgeführt, unabhängig davon, ob eine Exception aufgetreten ist. Üblicherweise werden dort Ressourcen wie Dateien oder Netzwerkverbindungen geschlossen.

try – catch – finally Java 
try {
    // Code
} catch (ExceptionA e1) {
    // Fehlerbehandlung
} catch (ExceptionB e2) {
    // Fehlerbehandlung
} finally {
    // Wird in jedem Fall ausgeführt.
    // Schließen etwaiger Ressourcen
}

Projektschritt 3.1

FirmaException statt Konsolenausgaben

Alle Set-Methoden, Konstruktoren und die Methoden der Firma werfen bei ungültigen Werten jetzt eine FirmaException – Standardwerte gibt es nicht mehr, ein ungültiges Objekt entsteht gar nicht erst. einstellen und einfuegen sind void und werfen im Fehlerfall; kuendigen(String) wirft, wenn niemand gefunden wird. compareTo darf (wegen des Interfaces) keine checked Exception werfen und verwendet daher eine unchecked NullPointerException. Die Tests prüfen mit assertThrows.

src/main/java/Firma.java (Auszug) Java 
public void einfuegen(int position, Person p) throws FirmaException {
    if (p == null) {
        throw new FirmaException("Fehler: ungueltiger Mitarbeiter: null");
    }
    if (position < 0 || position > personal.size()) {
        throw new FirmaException("Fehler: ungueltige Position " + position);
    }
    if (p.getFirma() != null) {
        throw new FirmaException("Fehler: " + p.getName() + " arbeitet schon bei "
                                 + p.getFirma().getName());
    }
    personal.add(position, p);
    p.setFirma(this);
}

public Person kuendigen(String name) throws FirmaException {
    if (name == null) {
        throw new FirmaException("Fehler: name ist null.");
    }
    for (int i = 0; i < personal.size(); i++) {
        if (name.equals(personal.get(i).getName())) {
            return kuendigen(i);
        }
    }
    throw new FirmaException("Fehler: kein Mitarbeiter mit Namen " + name);
}
src/main/java/Programm.java Java 
public class Programm {

    public static void main(String[] args) {
        try {
            Firma firma = new Firma("Spengergasse OG");
            firma.einstellen(new Angestellter("Susanne Huber", 1991, 20, 30, false));
            firma.einstellen(new Arbeiter("Karl Maier", 1989, 15, 40, true));
            firma.einstellen(new Freelancer("Sepp Gruber", 1981, 3, 300));
            firma.sortieren();
            firma.print();

            // Hier wird eine Exception geworfen (Geburtsjahr ungueltig) ...
            Arbeiter fehler = new Arbeiter("Karl Maier", 1789, 15, 40, false);

            // ... diese Zeilen werden daher nicht mehr ausgeführt
            firma.einstellen(fehler);
            firma.print();
        } catch (FirmaException e) {
            System.out.println("EXCEPTION: " + e.getMessage());
        }
    }
}

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: unreported exception

unreported exception FirmaException; must be caught or declared to be thrown.

Eine aufgerufene Methode wirft eine checked Exception. Entweder mit try/catch behandeln oder mit throws FirmaException an den eigenen Aufrufer weiterreichen.

Fehler: Exception verschluckt

catch (FirmaException e) { } – das Programm läuft weiter, als wäre nichts passiert, mit unvollständigen Daten.

Ein leerer catch-Block ist fast immer falsch. Mindestens die Meldung ausgeben bzw. dem Benutzer anzeigen – oder die Exception nicht fangen, sondern weiterreichen.

Fehler: throw vs. throws

public void setName(String n) throw FirmaException oder throws new FirmaException(…); übersetzt nicht.

throws (mit s) steht im Methodenkopf und deklariert; throw (ohne s) steht im Rumpf und wirft ein Exception-Objekt.

Quiz

4 Fragen · zum Aufklappen klicken

Frage 1 Warum ist eine Fehlermeldung mit System.out.println keine vollständige Fehlerbehandlung?

Erklärung: Eine Oberfläche oder ein anderes Programmteil sieht die Konsolenausgabe nicht. Eine Exception dagegen unterbricht den normalen Ablauf und kann vom Aufrufer gefangen und behandelt werden.

Frage 2 Was ist der Unterschied zwischen throw und throws?

Erklärung: throw new MeineException("…"); steht im Rumpf. public void tuWas() throws MeineException warnt alle Aufrufer: Diese Exception müsst ihr behandeln oder weitergeben.

Frage 3 Welche Aussage über checked und unchecked Exceptions stimmt?

Erklärung: Bei checked Exceptions prüft der Compiler, dass sich jemand darum kümmert. NullPointerException oder ArrayIndexOutOfBoundsException sind unchecked – sie zeigen meist Programmierfehler an.

Frage 4 Wann wird ein finally-Block ausgeführt?

Erklärung: finally eignet sich zum Aufräumen, etwa um eine Datei zu schließen, die im try-Block geöffnet wurde.
