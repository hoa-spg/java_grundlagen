1 — Zwei Arten, Parameter zu prüfen

In Teil 1 und 2 haben wir Parameter immer nach demselben Muster geprüft: Im if steht der positive Fall („der Wert ist gültig“), darin der normale Code, und im else die Fehlerbehandlung. Man nennt das den Happy Path – der „glückliche“ Weg steht innen.

Die Alternative: Man prüft zuerst auf den Fehlerfall und verlässt die Methode sofort mit return (oder, ab Lektion 3.1, mit einer Exception). Der normale Code steht danach – ohne else und ohne zusätzliche Einrückung. Das heißt Fail Early (früh scheitern), die Prüfungen am Methodenanfang heißen Guard Clauses (Wächter).

Happy Path (Teil 1 und 2) Java 
public void setStundenlohn(int stundenlohn) {
    if (stundenlohn > 7 && stundenlohn < 1000) {
        this.stundenlohn = stundenlohn;
    } else {
        System.out.println("Fehler: ungueltiger Stundenlohn: "
                           + stundenlohn);
    }
}
Fail Early (ab Teil 3) Java 
public void setStundenlohn(int stundenlohn) {
    if (stundenlohn <= 7 || stundenlohn >= 1000) {
        System.out.println("Fehler: ungueltiger Stundenlohn: "
                           + stundenlohn);
        return;
    }
    this.stundenlohn = stundenlohn;
}
💡
Fail Early ist der modernere Weg

In aktuellem, professionellem Code ist Fail Early der übliche Stil – Code-Richtlinien und Werkzeuge zur Codeanalyse empfehlen ihn ausdrücklich. Dass wir am Anfang anders vorgegangen sind, hatte nur didaktische Gründe: Eine positiv formulierte Bedingung („gültig ist 8 bis 999“) ist für Einsteiger leichter zu lesen als ihre Umkehrung, und jede Methode hat genau einen Weg nach unten bis zum Ende. Ab Teil 3 ist aller Code in diesem Kurs im Fail-Early-Stil geschrieben.

2 — Warum? Verschachtelung vermeiden

Bei einer einzigen Prüfung ist der Unterschied klein. Richtig deutlich wird er, wenn mehrere Bedingungen zusammenkommen. Hier hinzufuegen des Markts mit beidseitiger Assoziation aus Lektion 2.6 im Happy-Path-Stil:

Happy Path: jede Prüfung rückt den Code weiter nach rechts Java 
public boolean hinzufuegen(Stand stand) {
    boolean hinzugefuegt = false;
    if (stand != null) {
        if (anzahl < staende.length) {
            if (stand.getMarkt() == null) {
                staende[anzahl++] = stand;
                stand.setMarkt(this);
                hinzugefuegt = true;
            } else {
                System.out.println("Stand steht schon auf Markt " + stand.getMarkt().getName());
            }
        } else {
            System.out.println("Stand konnte nicht eingefuegt werden, kein Platz vorhanden.");
        }
    } else {
        System.out.println("Fehler: uebergebener Stand ist null.");
    }
    return hinzugefuegt;
}
Fail Early: erst alle Fehlerfälle ausschließen, dann der normale Ablauf Java

Die Methode liest sich jetzt wie eine Checkliste: Kein Stand? Abbruch. Kein Platz? Abbruch. Steht schon woanders? Abbruch. Sonst: einfügen.

3 — Bedingungen umkehren

Beim Umbau muss die Bedingung negiert werden. Am lesbarsten ist es, sie umzuformen, statt nur !( … ) davorzuschreiben:

gültig, wenn …Fehler, wenn …Regel
x > 7x <= 7Vergleich umdrehen: > ↔ <=, < ↔ >=, == ↔ !=
name != null && !name.isBlank()name == null || name.isBlank()De Morgan: aus && wird ||, jeder Teil wird umgekehrt
x >= 1900 && x <= 2050x < 1900 || x > 2050Bereich: außerhalb heißt „zu klein oder zu groß“
firma.enthaelt(this)!firma.enthaelt(this)Methodenaufruf: ! davor
a == null || a.isEmpty()a != null && !a.isEmpty()De Morgan in die andere Richtung
⚠
Kurzschlussauswertung beachten

In name == null || name.isBlank() ist die Reihenfolge wichtig: Ist name null, ist die Bedingung schon wahr und name.isBlank() wird gar nicht mehr aufgerufen – sonst gäbe es eine NullPointerException. Die null-Prüfung steht immer zuerst.

4 — Muster und Grenzen

Mit Rückgabewert

Fail Early mit return-Wert Java 
public int wert(int index) {
    if (index < 0 || index >= anzahl) {
        System.out.println("Fehler, ungueltiger Index: " + index);
        return -1;
    }
    return werte[index];
}

Mit Exceptions (ab Lektion 3.1)

Statt einer Meldung und return wirft die Guard Clause eine Exception – auch throw verlässt die Methode sofort:

Fail Early mit throw Java 
public void setName(String name) throws FirmaException {
    if (name == null || name.isBlank()) {
        throw new FirmaException("Fehler: ungueltiger Name: " + name);
    }
    this.name = name;
}

In Schleifen: continue

Elemente überspringen statt verschachteln Java 
for (Person p : personal) {
    if (!(p instanceof Mitarbeiter)) {
        continue;              // nächster Schleifendurchlauf
    }
    // ... nur Mitarbeiter verarbeiten
}

Wann nicht?

Fail Early gilt für Prüfungen, nach denen die Methode nicht sinnvoll weiterarbeiten kann. Eine Fallunterscheidung zwischen gleichwertigen Fällen bleibt eine if/else if-Kette – etwa die Zuordnung eines Textes zu einem Wert:

Fallunterscheidung: else if ist hier richtig Java 
if (tokens[5].equals("Facharbeiter")) {
    setFacharbeiter(true);
} else if (tokens[5].equals("Hilfsarbeiter")) {
    setFacharbeiter(false);
} else {
    throw new FirmaException("Facharbeiter/Hilfsarbeiter in 6. Spalte erwartet.");
}
ℹ
Ein return oder mehrere?

Früher galt die Regel „eine Methode, ein return am Ende“. Heute gilt sie als überholt: Mehrere return-Anweisungen sind unproblematisch, solange sie als Guard Clauses am Anfang stehen und die Methode kurz ist.

Häufige Fehler

Fehler: return vergessen

Die Fehlermeldung erscheint, aber der ungültige Wert wird trotzdem gesetzt.

Eine Guard Clause muss die Methode verlassen: return (bzw. throw) am Ende des Fehler-Blocks nicht vergessen.

Fehler: Falsch negiert

Aus x >= 1900 && x <= 2050 wird x < 1900 && x > 2050 – diese Bedingung ist nie wahr, ungültige Werte rutschen durch.

De Morgan: Beim Umkehren wird && zu || (und umgekehrt). Im Zweifel mit einem gültigen und zwei ungültigen Werten (zu klein, zu groß) testen.

Fehler: else nach return

if (x == null) { return; } else { … } – der Code ist wieder eingerückt, der Vorteil verloren.

Nach einem return oder throw ist else überflüssig. Den normalen Code einfach nach dem if-Block schreiben.

Wissenskontrolle

Frage 1 Was kennzeichnet den Fail-Early-Stil (Guard Clauses)?

Erklärung: Guard Clauses klären zuerst, was nicht passieren darf (if (fehler) { return; } bzw. später throw). Danach liest sich der eigentliche Code geradlinig.

Frage 2 Wie lautet die Umkehrung von alter >= 18?

Erklärung: Das Gegenteil von „mindestens 18“ ist „weniger als 18“. Bei <= wäre 18 in beiden Fällen enthalten.

Frage 3 Ein gültiger Wert liegt zwischen 10 und 100: wert >= 10 && wert <= 100. Welche Guard-Bedingung erkennt einen ungültigen Wert?

Erklärung: Nach De Morgan wird aus der Negation von A && B der Ausdruck !A || !B. Ein Wert kann nie gleichzeitig kleiner als 10 und größer als 100 sein – mit && würde die Prüfung nie anschlagen.

Frage 4 Wann bleibt eine else if-Kette trotz Fail Early richtig?

Erklärung: Guard Clauses sind für Fehlerfälle gedacht. Sind alle Zweige normale, gleichberechtigte Fälle, ist else if die klarste Schreibweise.
