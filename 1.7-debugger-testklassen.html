1 — Der Debugger

Der Debugger hält die Ausführung des Programms an, damit man den aktuellen Zustand – die Werte der Variablen und Eigenschaften – überprüfen kann. So lassen sich Fehler relativ einfach finden und beheben („de-buggen“). Jede Entwicklungsumgebung hat einen Debugger; Bedienung und Begriffe sind überall sehr ähnlich.

Haltepunkte (Breakpoints)

Ein Haltepunkt wird mit einem Klick in den Rand links neben einer Codezeile gesetzt (meist als roter Punkt dargestellt). Startet man das Programm im Debug-Modus bzw. ruft man eine Methode auf, hält die Ausführung an, bevor diese Zeile ausgeführt wird. Die aktuelle Zeile wird hervorgehoben.

Person.java – Haltepunkt in bmiAusgeben Java 
public void bmiAusgeben() {
    String bmiTyp = "";
    float bmi = bmiBerechnen();          // ● Haltepunkt: hier hält das Programm an
    if (maennlich) {
        if (bmi < 20) {
            bmiTyp = "Untergewicht";
        } else if (bmi <= 25) {
            bmiTyp = "Normalgewicht";
        } else {
            bmiTyp = "Übergewicht";
        }
    } else {
        // ...
    }
    System.out.println("BMI: " + bmi + " Typ: " + bmiTyp);
}

Was der Debugger anzeigt

Sobald das Programm steht, zeigt der Debugger drei Dinge:

Debugger-Ansicht (schematisch) beim Haltepunkt Text 
Aufrufkette (Call Stack)              Variablen
----------------------------          ------------------------------------------
> Person.bmiAusgeben()   Zeile 3      this = Person
  TestPerson.testBmi()   Zeile 7        name      = "Franz Maier"
                                        maennlich = true
                                        groesse   = 180
                                        gewicht   = 62
                                      bmiTyp = ""
                                      (bmi ist noch nicht berechnet)
  • Aufrufkette (Call Stack): welche Methode gerade läuft und von welcher Methode sie aufgerufen wurde – die oberste Zeile ist die aktuelle Methode.
  • Instanzvariablen (unter this): die Eigenschaften des Objekts, auf dem die Methode läuft.
  • Lokale Variablen und Parameter der aktuellen Methode. Variablen, die erst in späteren Zeilen deklariert werden, gibt es noch nicht.

Schrittweise ausführen

BefehlWirkungwann verwenden?
Step Over (oft nur „Step“)führt die aktuelle Zeile vollständig aus und hält in der nächsten Zeile derselben Methode an. Ein Methodenaufruf in der Zeile wird „in einem Rutsch“ ausgeführt.Normalfall: Zeile für Zeile durch die aktuelle Methode gehen
Step Intospringt in die Methode, die in der aktuellen Zeile aufgerufen wird, und hält in ihrer ersten Zeile anwenn man vermutet, dass der Fehler in der aufgerufenen Methode liegt
Step Out (Step Return)führt die aktuelle Methode bis zum Ende aus und hält beim Aufrufer wieder anwenn man versehentlich zu tief hineingesprungen ist
Continue (Resume)setzt die normale Ausführung fort, bis zum nächsten Haltepunkt oder Programmendewenn die interessante Stelle vorbei ist bzw. zum nächsten Haltepunkt
Stop (Terminate)bricht das Programm abz. B. bei einer Endlosschleife

💡
Gezielter anhalten

Die meisten Debugger bieten zusätzlich bedingte Haltepunkte (hält nur an, wenn z. B. i == 99) und Watches bzw. Evaluate Expression: beliebige Ausdrücke wie groesse / 100 während des Anhaltens ausrechnen lassen. Werte können im Debugger meist sogar geändert werden, um eine Vermutung auszuprobieren.

ℹ
Debugger statt println

Viele Anfänger streuen System.out.println in den Code, um Werte zu sehen. Der Debugger zeigt alle Werte, ohne den Code zu verändern – und man muss die Ausgaben danach nicht wieder entfernen.

2 — Testklassen

Um Fehler zu vermeiden, sind zahlreiche Tests unerlässlich. Ad-hoc-Tests – Objekte von Hand erstellen, befüllen und Methoden aufrufen – bedeuten erheblichen Aufwand: Nach jeder Änderung müssen alle Testschritte erneut durchgespielt werden, und neu entstandene Fehler werden leicht übersehen.

Testklassen spielen alle Testfälle auf Knopfdruck durch. Ein solches Programm mit main() kennst du schon aus Lektion 1.6 (TestMitarbeiter). Wird es größer, lohnt es sich, die Testfälle in eigene Methoden aufzuteilen, die main() nacheinander aufruft – hier für die Klasse Person aus Lektion 1.6:

TestPerson.java Java 
void main() {
    testPersonErzeugen();
}

void testPersonErzeugen() {
    Person p1 = new Person("Franz Maier", true, 180, 62);
    p1.printPerson();
    p1.bmiAusgeben();

    Person p2 = new Person("Sandra", false, 180, 62);
    p2.printPerson();
    p2.bmiAusgeben();

    Person p3 = new Person("Petra", false, 170, 50);
    p3.printPerson();
    p3.bmiAusgeben();

    Person p4 = new Person("Ferdinand", true, 181, 100);
    p4.printPerson();
    p4.bmiAusgeben();

    Person p6 = new Person("Elisa", false, 180, 59);
    p6.printPerson();
    p6.bmiAusgeben();

    Person p7 = null;
    p7.printPerson();   // provoziert eine NullPointerException
}

Testklassen gehören in den Ordner src/test/java. main() ruft die Testmethoden der Reihe nach auf; weitere Testfälle bekommen jeweils eine eigene Methode und eine Zeile in main().

ℹ
Grenze dieser Testklasse

Ob die Ergebnisse stimmen, muss man hier immer noch „mit dem Auge“ an der Konsolenausgabe prüfen. Das erledigt JUnit automatisch.

3 — JUnit-Testklassen

Die fortgeschrittene Variante ist der JUnit-Test. JUnit ist die Standard-Bibliothek für Tests in Java und in allen Entwicklungsumgebungen eingebaut. Üblicherweise gibt es zu einer Klasse Person eine Testklasse PersonTest; die Entwicklungsumgebung kann sie anlegen, man kann sie aber auch einfach selbst schreiben.

JUnit ist eine externe Bibliothek und muss dem Projekt einmal bekannt gemacht werden. In einem Maven-Projekt trägt man dazu in der pom.xml eine Abhängigkeit (dependency) ein und lässt Maven das Projekt neu laden (Maven-Symbol bzw. Reload); Maven lädt JUnit dann automatisch herunter. Was die pom.xml sonst enthält, zeigt Lektion 2.1.

pom.xml – Abhängigkeit für JUnit 5 (vor <build> einfügen) XML 
<dependencies>
    <dependency>
        <groupId>org.junit.jupiter</groupId>
        <artifactId>junit-jupiter</artifactId>
        <version>5.12.2</version>
        <scope>test</scope>
    </dependency>
</dependencies>

<scope>test</scope> heißt: JUnit steht nur den Klassen in src/test/java zur Verfügung, nicht dem eigentlichen Programm.

PersonTest.java Java 
import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

public class PersonTest {

    Person p;                                    // (1)

    /**
     * Sets up the test fixture. Called before every
     * test case method.
     */
    @BeforeEach                                  // (2)
    public void setUp() {
        p = new Person("David", true, 180, 80);
    }

    @Test                                        // (3)
    public void testBmiBerechnen() {
        assertTrue(p.bmiBerechnen() > 24.6);
        assertTrue(p.bmiBerechnen() < 24.7);
    }
}
  1. Eine Objekteigenschaft Person p macht die Person in der ganzen Testklasse verfügbar.
  2. Die Annotation @BeforeEach gibt an, dass diese Methode vor jedem Testfall ausgeführt wird. Hier werden Vorbereitungen getroffen – z. B. eine neue Instanz erzeugt.
  3. @Test kennzeichnet eine konkrete Testmethode. Oft gibt es zu jeder Methode einer Klasse eine (oder mehrere) Testmethoden. Mit Assertions wird das erwartete Verhalten sichergestellt.
⚠
assert ist kein Test

Java kennt auch ein Schlüsselwort assert(…). Es ist zur Laufzeit aber standardmäßig abgeschaltet – ein falscher Test würde unbemerkt „grün“. In JUnit verwendet man daher immer die Methoden aus Assertions: assertTrue, assertFalse, assertEquals, assertNull …

Assertionprüft
assertEquals(erwartet, tatsaechlich)Gleichheit; bei Kommazahlen mit Toleranz: assertEquals(24.69, bmi, 0.01)
assertTrue(bedingung) / assertFalse(bedingung)Bedingung ist wahr / falsch
assertNull(x) / assertNotNull(x)Referenz ist (nicht) null
assertSame(a, b)a und b verweisen auf dasselbe Objekt

Tests ausführen

Ausgeführt wird über das Kontextmenü der Testklasse bzw. den Run-Button neben der Klasse oder einer einzelnen Testmethode. Die IDE zeigt jeden Testfall mit grünem Haken (bestanden) oder rotem Kreuz (fehlgeschlagen) an, und bei einem Fehler, was erwartet wurde und was tatsächlich herauskam:

Testergebnis (schematisch), nachdem in bmiBerechnen ein Fehler eingebaut wurde Text 
PersonTest
  ✓ testAlter                         2 ms
  ✗ testBmiBerechnen                  5 ms

Tests: 2, Failures: 1, Errors: 0

org.opentest4j.AssertionFailedError: expected: <true> but was: <false>
    at PersonTest.testBmiBerechnen(PersonTest.java:19)
💡
Aussagekräftige Fehlermeldungen
assertTrue(bmi > 24.6) meldet nur „expected <true> but was <false>“. assertEquals(24.69, p.bmiBerechnen(), 0.01) meldet dagegen den tatsächlichen Wert, z. B. „expected: <24.69> but was: <2469.13>“ – damit ist der Fehler oft schon erkannt. Ein fehlschlagender Test lässt sich übrigens auch im Debugger starten: Haltepunkt in die Testmethode setzen und den Test mit Debug statt Run ausführen.

Projektschritt 1.7

Testklassen für den Mitarbeiter

Neben TestMitarbeiter (Lektion 1.6), deren Ausgabe du selbst kontrollierst, kommt jetzt eine JUnit-Testklasse, die selbst prüft. Trage die JUnit-Abhängigkeit in die pom.xml ein, lege MitarbeiterTest in src/test/java an und führe sie aus. Baue absichtlich einen Fehler in getKostenProMonat ein (z. B. 3 statt 4 Wochen) und beobachte, welcher Test rot wird – und vergleiche, wie schnell du denselben Fehler in der Ausgabe von TestMitarbeiter findest.

src/test/java/MitarbeiterTest.java Java 
import static org.junit.jupiter.api.Assertions.*;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

/**
 * JUnit-Testklasse zu Mitarbeiter.
 * Ausführen: grüner Pfeil neben der Klasse bzw. einer Testmethode.
 */
public class MitarbeiterTest {

    private Mitarbeiter m;

    @BeforeEach
    public void setUp() {
        m = new Mitarbeiter("Karl Maier", 1989, 15, 40);
    }

    @Test
    public void testKostenProMonat() {
        assertEquals(2400, m.getKostenProMonat());
        assertEquals(3000, m.getKostenProMonat(5));
    }

    @Test
    public void testAlter() {
        assertEquals(37, m.alterBerechnen(2026));
    }

    @Test
    public void testUngueltigeWerte() {
        m.setStundenlohn(5);
        assertEquals(10, m.getStundenlohn());   // Standardwert
        m.setGeburtsjahr(1789);
        assertEquals(1970, m.getGeburtsjahr());
    }

    @Test
    public void testTeilzeit() {
        assertFalse(m.isTeilzeit());
        m.setAnzahlWochenStunden(20);
        assertTrue(m.isTeilzeit());
        assertEquals(4.0, m.stundenProTag(), 0.001);
    }
}

Häufige Fehler

3 Fehler · zum Aufklappen klicken
Fehler: Test wird nicht ausgeführt

Eine Testmethode erscheint nicht in den Ergebnissen.

Die Annotation @Test fehlt, oder die Methode ist static bzw. hat Parameter. Testmethoden sind nicht statisch, void und parameterlos.

Fehler: Kommazahlen exakt verglichen

assertEquals(24.69, p.bmiBerechnen()) schlägt fehl, obwohl der Wert „stimmt“.

Kommazahlen sind nicht exakt darstellbar. Mit Toleranz vergleichen: assertEquals(24.69, p.bmiBerechnen(), 0.01).

Fehler: Tests hängen voneinander ab

Ein Test funktioniert nur, wenn vorher ein anderer gelaufen ist (z. B. weil er den Namen ändert).

Jeder Test muss für sich allein laufen. Gemeinsame Vorbereitung gehört in @BeforeEach – dort wird vor jedem Test ein frisches Objekt erzeugt.

Quiz

4 Fragen · zum Aufklappen klicken

Frage 1 Das Programm steht im Debugger an einer Zeile mit dem Aufruf berechne(). Welcher Befehl springt in diese Methode hinein?

Erklärung: Step Into folgt dem Methodenaufruf. Step Over führt die ganze Zeile aus und hält in der nächsten Zeile an, Step Out läuft bis zum Ende der aktuellen Methode, Continue bis zum nächsten Haltepunkt.

Frage 2 Was zeigt der Call Stack im Debugger?

Erklärung: Ganz oben steht die Methode, in der das Programm gerade steht, darunter jeweils die Methode, die sie aufgerufen hat – bis hinunter zu main bzw. dem Test.

Frage 3 Welche Vorteile hat ein JUnit-Test gegenüber einer Testklasse, die nur Werte ausgibt?

Mehrere Antworten sind richtig.

Erklärung: Ein JUnit-Test vergleicht selbst mit den erwarteten Werten und meldet Abweichungen – niemand muss Ausgaben kontrollieren. Deshalb lässt er sich nach jeder Änderung auf Knopfdruck wiederholen. Alle Fehler eines Programms findet aber auch er nicht.

Frage 4 Wozu dient eine Methode mit @BeforeEach in einer JUnit-Testklasse?

Erklärung: Dank @BeforeEach startet jeder Test mit denselben, unveränderten Objekten. So beeinflussen sich die Tests nicht gegenseitig.
